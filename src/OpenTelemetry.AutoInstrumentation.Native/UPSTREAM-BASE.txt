WHY THIS FILE EXISTS
--------------------
Without a recorded base commit, the first rebase onto a newer upstream has nothing to
diff against. That is not a cosmetic problem: an incomplete merge here produces a
binary that COMPILES CLEAN AND FAILS ONLY AT dlopen (see "THE FAILURE MODE" below).
The base commit is what makes `git diff <base>..<new-tag> -- <subtree>` a reliable
answer to "what did upstream change under me."

PTHREAD LINK — A DELTA UPSTREAM DOES NOT HAVE
---------------------------------------------
CMakeLists.txt additionally gains `find_package(Threads REQUIRED)` and `Threads::Threads` on the
ISLINUX link line. This is OURS, not upstream's, and it is required by the old-glibc build:

  glibc >= 2.34 folded libpthread INTO libc, so on a modern build host pthread_create resolves
  from libc.so.6 and no DT_NEEDED entry is emitted. Upstream builds their released binaries that
  way, and `readelf -d` on their shipped .so confirms it lists only libm/libc/ld-linux — no
  libpthread. On glibc 2.23 libpthread is still separate, so the same source produces a library
  that BUILDS AND LINKS CLEAN, loads fine on a modern distro, and fails at dlopen on an old one:

      undefined symbol: pthread_create

  Measured, not assumed: `ldd -r` reported pthread_create as the ONLY unresolved symbol.

  Consequence for rebasing: do NOT drop this hunk when re-applying the delta. Upstream has no
  reason to add it, so it will not appear in their tree, and losing it re-introduces a defect that
  only the dlopen gate on an old-glibc image can see.

The delta is purely ADDITIVE (one deleted line total) and touches none of the
CallTarget function-level path. That is what bounds rebase drift.

Exports added by the delta, absent from the stock upstream binary:
  AddLineProbes
  RemoveLineProbe

THE FAILURE MODE TO KNOW ABOUT — READ BEFORE REBASING
-----------------------------------------------------
An incomplete vendored tree BUILDS SUCCESSFULLY and fails only when the CLR tries to
load the profiler. A missing source file yields a shared library with an undefined
symbol; `ldd` still reports it as loadable. Only a real dlopen + dlsym catches it.
Two consequences:

  1. A green build is NOT evidence that the binary loads. Every RID must pass a
     dlopen+dlsym gate (LoadLibrary+GetProcAddress on Windows) that asserts the SYMBOL
     resolves, not merely that the library opens.
  2. After any rebase, re-check the source lists. Upstream adding a .cpp means adding
     it in TWO places, which are maintained independently:
       - CMakeLists.txt  (non-Windows)
       - OpenTelemetry.AutoInstrumentation.Native.vcxproj  (Windows; lists sources
         explicitly, so an omission here is a LINK error on Windows only)

VERSION PIN
-----------
The native profiler locates its managed half by strong name, built from
OTEL_AUTO_VERSION_MAJOR (version.h → ASSEMBLY_VERSION → otel_profiler_constants.h).
It must be built with UPSTREAM's major version, not this distro's. See
build/Build.NativeProfiler.cs for the pin and the assertion that enforces it.
